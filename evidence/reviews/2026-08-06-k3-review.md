## F1 — watcher dies on missing fswatch, log promises "supervisor restart" that never comes
SEVERITY: LOSES-WORK (silence class: every push-wake seat goes dead and the log claims recovery is underway)
FILE: tool/bin/watch.sh:1283 (fswatch exec), and the supervisor-restart message near it
WHAT HAPPENS: On a machine without fswatch on PATH (a new operator who has not
installed it, or any non-homebrew PATH), the auto-started watcher prints
"fswatch died on a live pad — exiting for supervisor restart" and exits. No
supervisor ever restarts it: the launcher process is gone, the lock heartbeat
goes stale (observed 87s+), `stitchpad watch status` says "no watcher running".
The pad silently has no wake delivery until some LATER command happens to call
ensure-watcher again. Nothing tells the operator "install fswatch" — the only
hint is buried in .stitchpad/.state/watch.log, and even that log line lies
about a restart being in progress.
PROOF:
  $ env -i HOME=/tmp/blindspot/home PATH=/usr/bin:/bin:/usr/local/bin TERM=xterm \
      bash -c 'stitchpad init; stitchpad join alice cli'   # fswatch absent from PATH
  $ tail -3 .stitchpad/.state/watch.log
  /private/tmp/wt-merge/tool/bin/watch.sh: line 1283: fswatch: command not found
  [stitchpad] fswatch died on a live pad — exiting for supervisor restart
  $ perl -e 'select(undef,undef,undef,87)'; date +%s; cat .stitchpad/.state/watch.lock.d/heartbeat
  1785996898
  1785996811                      # heartbeat 87s stale; launcher pid 14082 dead (ps -p 14082 -> empty)
  $ stitchpad watch status
  no watcher running              # rc=1 — the promised restart never happened
FIX: in watch.sh, preflight `command -v fswatch` before entering the supervise
loop; if absent, print "fswatch is required — brew install fswatch" to STDERR
and exit non-zero WITHOUT the "supervisor restart" wording. Optionally have
ensure_watcher surface that failure on the next command instead of only in a
log file nobody is told about.

## F4 — third-party `wake <pull-seat>` burns the seat's cursor: message printed to the WRONG stdout, agent never sees it
SEVERITY: LOSES-WORK (category 1 in its purest form — the exact shape the code's own comment calls "the single most expensive shape in this system")
FILE: tool/bin/stitchpad:3416-3427 (the PUSH-SEAT MISDIRECTION GUARD — its condition `[ "$(sp_wake_mode_for "$who")" = "push" ]` leaves pull seats unguarded)
WHAT HAPPENS: The guard in the wake arm refuses a third-party consuming wake
only when the target is a PUSH seat. For a PULL seat, ANY caller whose identity
is not the seat gets the seat's pending mention printed to THEIR stdout, rc=0,
and seen.<name> advances — so when the seat's own runtime polls a moment later
there is nothing. The message was consumed, acked by the cursor, and never
received. The seat then looks exactly like an idle/unresponsive seat. The
guard's own comment describes this shape as "total loss ... it looks exactly
like success" — and the fix shipped only covers push. The first-run trap is
real: `stitchpad wake [name]` is advertised in help as "print new @name
messages since last drain", which is precisely what an operator types to check
on a seat.
PROOF:
  $ stitchpad join carol cli; stitchpad join dave cli
  $ STITCHPAD_NAME=dave stitchpad say "@carol please review the plan"
  $ STITCHPAD_NAME=dave stitchpad wake carol        # operator "checks on carol"
  pasture: NEW from @dave — @carol please review the plan — reply with @dave ...
  wake-by-other rc=0                                 # printed to DAVE; consumed
  $ STITCHPAD_NAME=carol stitchpad wake carol        # carol polls for herself
  (empty)                            carol wake rc=0  # NOTHING — she never sees it
  $ cat .stitchpad/.state/seen.carol
  1                                                  # cursor burned by dave's call
FIX: drop the push-only condition — the misdirection is third-party-ness, not
wake mode. A pull seat's legitimate poll always arrives with _caller == who
(its own bound terminal / STITCHPAD_NAME), so refusing every _caller != who
consuming wake has no false positives:
  --- a/tool/bin/stitchpad
  +++ b/tool/bin/stitchpad
  @@
  -      if [ "$_caller" != "$who" ] && [ "$(sp_wake_mode_for "$who")" = "push" ]; then
  -        echo "stitchpad: REFUSED — @$who is a PUSH seat; \`wake\` would print its message here and burn its cursor without delivering anything." >&2
  +      if [ "$_caller" != "$who" ]; then
  +        echo "stitchpad: REFUSED — \`wake $who\` from this terminal would print @${who}'s message here and burn their cursor without delivering anything." >&2
  (keep the three hint lines; the push hint about the watcher stays correct for
  push seats, and --peek remains the sanctioned look-don't-touch path.)
